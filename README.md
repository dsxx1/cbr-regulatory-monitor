Наблюдатель, который два раза в рабочий день опрашивает API разъяснений ЦБ,
находит новые и изменившиеся требования и публикует отчёт. Работает на GitHub Actions,
бесплатно, без сервера и без карты.

Это первая очередь: **обнаружение и фиксация**. Анализ моделью, карточки решений
и задачи в Битрикс24 подключаются следующими шагами — контур описан в
`2026-09-11-claude-regulatory-decision-system.md`.

## Режимы

Режим определяется наличием секретов, а не правкой кода.

| Режим | Условие | Что делает |
|---|---|---|
| **Тень** | секретов нет | обнаружение и отчёт, наружу ничего |
| **Полуавто** | задан `LLM_API_KEY` | добавляется анализ, очередь заполняется |
| **Авто** | задан `B24_WEBHOOK` **и** флаг `--send` | отправка в Битрикс24 |

Сейчас работает **тень**. Переход в «авто» требует двух независимых действий:
выдать секрет и явно добавить флаг. Одного секрета мало — случайно включить
отправку нельзя.

## Как это работает

Один прогон делает шесть вещей:

1. Читает дерево категорий и замечает **появление новых подкатегорий** — иначе новый
   раздел останется незамеченным навсегда.
2. Забирает разъяснения по наблюдаемым категориям (по умолчанию 774 и 378).
3. Снимает теги и сущности, схлопывает пробелы и считает хеш **нормализованного
   текста**. Переверстают страницу — ложного сигнала не будет.
4. Сравнивает с прошлым прогоном: новое, изменилось, без изменений.
5. Отличает **отказ источника от отсутствия изменений**. Это разные события, и путать
   их нельзя: молчащий источник выглядит как «всё спокойно».
6. Сохраняет состояние и рисует отчёт.

Прогон идемпотентен: повторный запуск на тех же данных даёт ноль новых.

Поле `modification` из API — это время правки разъяснения, **не дата вступления
требования в силу**. Оно хранится, но сигналом не считается; дату вступления
подтверждает человек.

## Запуск локально

Нужен Python 3.9 или новее. Зависимостей нет.

```bash
python watch_cbr.py
```

Полезные ключи:

```bash
python watch_cbr.py --categories 774 378 426 --state state.json --report docs/index.html
```

`--fail-on-source-error` возвращает код 2, если источник не ответил. По умолчанию
прогон завершается успешно, а отказ виден в отчёте — чтобы временная недоступность
сайта ЦБ не заваливала почту красными письмами.

### Где смотреть результат

**Вкладка Actions.** У каждого прогона на странице есть сводка: сколько новых,
сколько изменилось, сколько под наблюдением, были ли отказы источников. Читать логи
не нужно — таблица видна сразу.

**Артефакт `otchet`.** Там же, внизу страницы прогона, лежит `index.html` —
полный отчёт, скачивается и открывается в браузере. Хранится 30 дней.

**Файл в репозитории.** `docs/index.html` обновляется каждым прогоном, история
изменений видна через git.

### Почему нет постоянной ссылки

GitHub Pages публикует `docs/index.html` отдельным workflow `pages.yml`. Перед первым
запуском в Settings → Pages нужно выбрать **GitHub Actions** как источник публикации.

Варианты, если постоянная ссылка всё-таки нужна:

- открыть Pages URL после первого успешного workflow;
- при необходимости использовать артефакт `otchet` как резервную копию.

## Бесплатный бот Битрикс24

Для сообщений именно от бота, а не от вашей учётной записи, используется папка
`worker/`: GitHub передаёт подписанную карточку, а бесплатный Cloudflare Worker
отправляет её в зарегистрированный ChatBot v2. До появления `SEND_TO_BOT=yes`
уведомления не отправляются. Оператор задаёт секреты Worker по `worker/README.md`;
значения не добавляются в Git.

## Работа с репозиторием локально

Важная особенность: **workflow сам коммитит состояние после каждого прогона**,
поэтому локальная копия постоянно отстаёт от origin. Перед своим пушем всегда:

```bash
git pull --rebase
```

Без этого push молча отклоняется как non-fast-forward, и правка не доезжает —
workflow продолжает работать со старой версией.

## Расписание

```
'0 6 * * 1-5'    09:00 МСК
'30 9 * * 1-5'   12:30 МСК
```

Время в UTC, Москва — UTC+3. Оба окна выбраны не случайно: они попадают в льготный
тариф DeepSeek (06:00–10:00 UTC), поэтому когда добавится анализ моделью, он будет
стоить вдвое дешевле.

Два прогона в сутки — не экономия, а следствие задачи. Срочность считается в днях и
месяцах, задержка обнаружения на 12 часов не меняет ни один уровень.

Расписание GitHub Actions **опаздывает** под нагрузкой платформы, иногда на десятки
минут. Для этой задачи безразлично, но опираться на точное время нельзя.

## Известные границы

- Наблюдаются только разъяснения. RSS, проекты НПА и общие требования к НФО — следующий шаг.
  Разъяснение вообще **не является нормой**, это позиция регулятора.
- Фильтра по применимости нет: всё, что нашлось, попадает в отчёт целиком.
  Применимость подтверждает человек — это шлюз 1 решающего контура.
- Состояние PowerShell-прототипа и Python-версии **несовместимы**: нормализация текста
  отличается, хеши разные. Запускать что-то одно.
- Каждый прогон делает коммит, даже когда изменений нет: в состоянии меняются отметки
  времени. Это осознанно — так репозиторий остаётся активным, и GitHub не отключает
  расписание за бездействие.
